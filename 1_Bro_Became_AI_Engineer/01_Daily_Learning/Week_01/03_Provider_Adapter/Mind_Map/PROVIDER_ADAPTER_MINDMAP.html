Provider Adapter

A 30–90 second master recall map for keeping model providers replaceable, observable, testable, and outside business logic.

Core mental model

The application owns the contract. Infrastructure translates the provider.

A PORT / INTERFACE states what model capability the product needs. A PROVIDER ADAPTER converts that stable contract to one provider SDK—and normalizes the result back.

PORT = WHAT Application-owned capability and semantics.
ADAPTER = HOW Provider-specific request, response, stream, and error translation.
PORTABLE ≠ IDENTICAL Providers still differ in capabilities, behavior, limits, and metadata.

Why the Boundary Exists

Problem solved
  • Stops SDK types leaking into business code
  • Localizes provider/model changes
  • Makes unit tests network-free
  • Standardizes streaming, usage, and errors
Warning

A wrapper that returns raw provider objects is still provider coupling.

Provider change should mostly affect configuration or infrastructure—not use cases.

Port vs Adapter vs SDK

Port / Interface

Application-owned contract describing the capability required.

Provider Adapter

Infrastructure implementation translating the port to one provider.

SDK

Provider-owned implementation detail kept at the edge.

PORT → what · ADAPTER → translation · SDK → external detail.

Translate & Normalize

Adapter owns
  • Message / system-instruction mapping
  • Provider request construction
  • Response and usage extraction
  • Finish-reason and error mapping
Decision rule

Reject, deliberately degrade, or route when a required capability is unsupported.

Never silently discard an important field.

Capabilities & Trade-offs

Common core

Text generation, streaming, usage, finish reason, request ID.

Optional capabilities
  • Structured output
  • Tool calling
  • Multimodal input
  • Embeddings
Trade-off

Lowest common denominator is portable but may hide provider strengths.

Small shared core + explicit capability ports.
6

Failures, Retries & Streaming

Stable error categories
  • Authentication / invalid request → do not retry
  • Rate limit / timeout / connection / 5xx → bounded retry only
  • Content blocked → safe explicit outcome
Streaming

Sequence of events—not a slowly returned string. Partial output is not validated output.

Application retry × SDK retry × proxy retry = request multiplication.
7

Trust, Security & Observability

Trust boundaries
  • Application policy → trusted deterministic code
  • User / retrieved data → untrusted
  • Model output → untrusted until validated
Safe operations
  • Keys server-side via environment / secret manager
  • Redact prompts, documents, headers, and credentials
  • Record provider, model, latency, usage, retry, status
The adapter controls access to a provider—not authorization or business policy.

Decision Recall

Direct SDK Best for intentionally disposable experiments and tiny one-provider scripts.
Provider Adapter Best when testing, switching, evaluation, streaming, or production operations matter.
One Generic Adapter Faster for closely compatible endpoints; differences may be hidden.
Provider-Specific Adapters Better when capabilities, errors, usage, or native features materially differ.

Protected Responsibilities

These never become prompt-only or model-owned decisions:

  • Authentication and authorization
  • Tenant / resource isolation
  • Billing entitlements and quotas
  • Destructive-action permission
  • Secret handling and logging policy
  • Final output validation
